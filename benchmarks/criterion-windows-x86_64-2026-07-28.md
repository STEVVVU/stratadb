# Criterion results — 2026-07-28

Generated by `cargo bench --bench engine` and
`cargo bench --features compare --bench comparison`.

## Environment

| Item | Value |
| --- | --- |
| CPU | Intel Core Ultra 7 265U (12 cores / 14 threads) |
| RAM | 31.4 GB |
| Storage | Samsung MZVL2512HCJQ-00BH1 NVMe SSD |
| OS | Windows 11 Enterprise, build 26200 |
| Toolchain | rustc 1.96.0 (ac68faa20 2026-05-25), release + `lto = "thin"` |
| criterion | 0.7.0 |

**Read the ranges, not the midpoints.** Every figure below is criterion's
`[lower estimate upper]` confidence interval. This is a power-managed laptop CPU
with no pinned clocks and a consumer NVMe drive with an SLC cache and its own
write-back behavior; several groups reported 7-13% outliers. Intervals here are
wide, and the honest reading of two overlapping intervals is "not distinguished
by this measurement," not "the midpoints differ."

All write benchmarks are fully durable: StrataDB `sync_data`s before every
`write` returns, and this is not configurable.

## Engine benchmarks

### Durable writes

| Benchmark | Time (lower / est. / upper) | Throughput (est.) |
| --- | --- | ---: |
| `write/single-durable/sequential` (500 ops) | 1.3315 s / 1.3965 s / 1.4696 s | 358 ops/s |
| `write/single-durable/random` (500 ops) | 1.3491 s / 1.6015 s / 1.9395 s | 312 ops/s |

Sequential and random are within each other's intervals, which is the expected
result: the engine appends to a log, so insertion order does not affect write
placement. There is no B-tree to split. A gap here would have indicated an
unintended ordering dependency.

### Batch size vs. throughput (2,000 ops per iteration)

| Batch size | Time (lower / est. / upper) | Throughput (est.) |
| ---: | --- | ---: |
| 1 | 5.0596 s / 5.3042 s / 5.5883 s | 377 ops/s |
| 10 | 557.48 ms / 630.96 ms / 722.67 ms | 3,170 ops/s |
| 100 | 65.857 ms / 71.205 ms / 77.375 ms | 28,088 ops/s |
| 1000 | 10.795 ms / 11.792 ms / 12.896 ms | 169,610 ops/s |

This is the most informative group in the suite. Throughput scales almost
linearly with batch size across three orders of magnitude — 1 → 1000 is a ~450x
improvement for a 1000x reduction in fsync count. That near-linearity is the
direct measurement of the claim that a batch is one record and one fsync: almost
all per-operation cost at small batch sizes is synchronization, not encoding or
appending. Callers who need throughput must batch.

### Point reads (20,000 keys resident)

| Benchmark | Time (lower / est. / upper) | Throughput (est.) |
| --- | --- | ---: |
| `read/point/hit/sequential` | 6.3351 µs / 9.1180 µs / 12.819 µs | 110 Kelem/s |
| `read/point/hit/random` | 16.338 µs / 18.386 µs / 20.686 µs | 54 Kelem/s |
| `read/point/miss` | 567.75 ns / 661.96 ns / 760.49 ns | 1.51 Melem/s |

A miss is ~28x faster than a random hit, and a miss does no I/O at all — it is
the `BTreeMap` lookup and nothing else. So roughly 96% of a point read is the
positional read plus the value allocation, and only ~4% is index lookup. That
ratio is what motivated the mmap experiment described in the README; see there
for why mmap was measured, found faster, and still not adopted.

Sequential hits beat random hits by ~2x, which is the OS page cache: reading keys
in key order walks the segment file in offset order.

### Snapshots and compaction

| Benchmark | Time (lower / est. / upper) | Throughput (est.) |
| --- | --- | ---: |
| `snapshot/materialize/1000-keys` | 7.4258 ms / 8.3837 ms / 9.4848 ms | 119 Kelem/s |
| `snapshot/materialize/10000-keys` | 82.257 ms / 94.008 ms / 109.94 ms | 106 Kelem/s |
| `compaction/5000-keys-3-versions` | 137.00 ms / 215.78 ms / 307.57 ms | 5.66 MiB/s |

Snapshot per-key throughput is essentially flat from 1K to 10K keys (119K vs
106K elem/s), confirming that `snapshot` is linear in live data size. It copies
every live value into an `Arc<BTreeMap>`, so a 10K-key snapshot costs ~94 ms and
the cost is paid per snapshot, not amortized.

### Recovery vs. WAL size

| Keys | WAL bytes | Time (lower / est. / upper) | Throughput (est.) |
| ---: | ---: | --- | ---: |
| 1,000 | 279,056 | 6.2877 ms / 9.7820 ms / 15.046 ms | 27.2 MiB/s |
| 10,000 | 2,790,560 | 32.827 ms / 42.735 ms / 54.886 ms | 62.3 MiB/s |
| 50,000 | 13,952,800 | 98.681 ms / 115.46 ms / 139.37 ms | 115.2 MiB/s |

Recovery is linear in bytes on disk, as designed: every record is re-read and
every CRC re-verified to rebuild the index. Per-byte throughput *improves* with
size (27 → 115 MiB/s) because fixed per-open costs dominate the small case.

The absolute numbers are the important part: ~115 ms to reopen a 14 MB database.
Extrapolating the 50K-key rate, a 1 GB WAL implies roughly 9 s of startup time,
and the index must also fit in RAM. This is the engine's principal scaling limit
and it is a direct consequence of choosing a full in-memory index with no
checkpoint. See the comparison against redb below.

### Format and checksum (CPU only, no I/O)

| Benchmark | Time (lower / est. / upper) | Throughput (est.) |
| --- | --- | ---: |
| `crc32/accelerated/256B` | 23.725 ns / 27.062 ns / 31.537 ns | 8.81 GiB/s |
| `crc32/reference/256B` | 2.2329 µs / 2.5818 µs / 2.9770 µs | 94.6 MiB/s |
| `crc32/accelerated/4096B` | 268.76 ns / 289.63 ns / 311.93 ns | 13.17 GiB/s |
| `crc32/reference/4096B` | 38.916 µs / 48.378 µs / 59.649 µs | 80.7 MiB/s |
| `crc32/accelerated/65536B` | 4.6680 µs / 5.0918 µs / 5.5779 µs | 11.99 GiB/s |
| `crc32/reference/65536B` | 820.14 µs / 975.78 µs / 1.1449 ms | 64.1 MiB/s |
| `encode-batch/100-ops` | 48.745 µs / 54.682 µs / 61.341 µs | 1.83 Melem/s |

`crc32fast` is **~95x faster at 256 B and ~190x faster at 64 KiB** than the
bitwise reference implementation (13.17 GiB/s vs 80.7 MiB/s at 4 KiB). The
reference processes one bit at a time with no lookup table; `crc32fast` uses
PCLMULQDQ. Both produce identical output, enforced by the differential test in
`src/crc32.rs`.

Honest caveat on what this bought: at 256-byte values the checksum went from
~2.6 µs to ~27 ns, a ~2.5 µs saving per record — against a durable write that
costs ~2.8 ms (batch-1 above). So the CRC swap is worth roughly **0.1% of a
single durable write** and is invisible in every I/O-bound benchmark in this
file. It matters where CRC cost is actually on the critical path: recovery, which
verifies every record with no fsync in the loop, and large-value or heavily
batched writes.

## Comparison: StrataDB vs. redb 2.6.3 vs. sled 0.34.7

Both comparison engines are pure Rust. `rocksdb` was not used: `librocksdb-sys`
requires a C++ toolchain and is slow and failure-prone on Windows/MSVC.

**Durability parity.** redb defaults to `Durability::Immediate` (fsync on
commit), so it is compared as-is. sled defaults to `flush_every_ms(500)` and
returns from `insert` *before* data is durable, so sled is measured twice:
`sled-durable` (`flush_every_ms(None)` plus an explicit `flush()`) is the
apples-to-apples number, and `sled-default` is stock configuration shown only to
quantify what the guarantee costs.

### Individual durable writes — 300 ops, one fsync each

| Engine | Time (lower / est. / upper) | Throughput (est.) |
| --- | --- | ---: |
| **StrataDB** | 749.97 ms / 771.94 ms / 796.70 ms | **389 ops/s** |
| sled-durable | 853.38 ms / 926.47 ms / 1.0218 s | 324 ops/s |
| redb | 1.1602 s / 1.2095 s / 1.2818 s | 248 ops/s |
| _sled-default (not durable)_ | _9.8038 ms / 14.789 ms / 17.478 ms_ | _20,286 ops/s_ |

StrataDB is fastest, ~1.2x over sled-durable and ~1.6x over redb. This is the
expected shape and not much of a boast: an append-only log does the least
possible work per durable write — one append, one fsync, one in-memory index
insert. redb must maintain a copy-on-write B-tree and commit a transaction.

The `sled-default` row is the most useful number in the table: **~52x faster
than sled-durable**, purely from not waiting for the disk. Any comparison that
puts stock sled against a synchronously-fsyncing engine is measuring that gap
and nothing else.

### Batched durable writes — 5,000 ops in batches of 100

| Engine | Time (lower / est. / upper) | Throughput (est.) |
| --- | --- | ---: |
| **StrataDB** | 141.69 ms / 158.67 ms / 176.23 ms | **31.5 Kops/s** |
| redb | 267.64 ms / 276.65 ms / 290.81 ms | 18.1 Kops/s |
| sled-durable | 311.84 ms / 333.58 ms / 353.25 ms | 15.0 Kops/s |

StrataDB leads by ~1.7x over redb and ~2.1x over sled-durable. Again structural:
a 100-operation batch is one WAL record, one append, one fsync.

### Random point reads — 20,000 keys, default configuration

| Engine | Time (lower / est. / upper) | Throughput (est.) |
| --- | --- | ---: |
| **sled** | 3.3408 µs / 3.5232 µs / 3.7077 µs | **284 Kelem/s** |
| redb | 4.6251 µs / 4.8454 µs / 5.0724 µs | 206 Kelem/s |
| _StrataDB_ | _31.907 µs / 38.321 µs / 45.213 µs_ | _26 Kelem/s_ |

**StrataDB loses badly — about 11x slower than sled and 8x slower than redb.**
This is the headline loss and it deserves a straight explanation.

It is not the index. `read/point/miss` above shows the index lookup costs ~662 ns;
StrataDB's problem is everything after it. Each hit issues a fresh `seek_read`
syscall and allocates a new `Vec<u8>` for the value. redb and sled both maintain
their own page/block cache in user space and can serve a repeat read from cached
pages with no syscall, and both return borrowed or reference-counted bytes
(`AccessGuard`, `IVec`) instead of copying into a new allocation.

So StrataDB pays a syscall plus a heap allocation on *every* read, while the
others pay neither on a cache hit. Two absent features — a block cache and a
zero-copy read API — account for essentially the entire gap. Both are listed as
known limits in the README, and neither is a bug; they are the cost of the
simpler design. The mmap experiment (see README) confirms the diagnosis: removing
just the syscall recovers ~19x.

### Opening an existing 50,000-key database

| Engine | Time (lower / est. / upper) |
| --- | --- |
| **redb** | 8.9016 ms / 9.7789 ms / 11.744 ms |
| sled | 36.337 ms / 39.611 ms / 42.606 ms |
| _StrataDB_ | _404.64 ms / 486.26 ms / 579.83 ms_ |

**StrataDB loses by ~50x against redb and ~12x against sled, and the gap grows
with database size.** This is the most serious structural weakness in the design.

StrataDB has no checkpoint and no on-disk index. To answer the first `get` it
must replay every record in every segment, verify every CRC, and rebuild the
whole `BTreeMap`. Startup is therefore O(bytes on disk). redb stores its B-tree
on disk and only reads the root plus metadata at open — near-constant time. sled
reads its metadata and lazily pages in.

Worth stating plainly: redb wins here *because it did the work earlier*, keeping
its index durable as part of each commit, which is part of why it is slower on
the write benchmarks above. That is the real trade this table exposes — StrataDB
buys its write advantage by deferring index construction to startup. A manifest
plus periodic index checkpoint is the standard fix and is not implemented.

## Summary

| Axis | Winner | StrataDB's position |
| --- | --- | --- |
| Individual durable writes | StrataDB | 1.2x over sled-durable, 1.6x over redb |
| Batched durable writes | StrataDB | 1.7x over redb, 2.1x over sled-durable |
| Random point reads | sled | **~11x slower** (no block cache, no zero-copy read) |
| Open existing database | redb | **~50x slower**, and worsens with size |
| Range scans / ordered iteration | redb, sled | **not implemented** |

StrataDB wins on durable write throughput, which is what a log-structured design
is for, and loses on reads and startup, which is what it traded away. Neither
result is surprising, and the losses are larger than the wins.
